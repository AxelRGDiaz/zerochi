# Contracts

The TypeScript source of truth for frontend DTOs is `src/types`; Rust command DTOs must serialize to the same field names and meanings. Breaking changes require Lead review and a contract test.

## Domain records

- `MailAccount`: stable local id, email/display name, optional `provider` (`"gmail"` | `"outlook"`; absent means Gmail and only `"outlook"` is serialized), active flag, Zerochi pending count, optional Gmail INBOX unread count serialized as `inboxUnreadCount`, optional history cursor and sync time. `pendingCount` and the Gmail INBOX unread count are distinct and must never be substituted for one another.
- `MailMessage`: provider message/thread ids, account id, metadata, detection time, optional local-open time. Never store bodies in V1.
- `InboxPetSnapshot`: global Gmail INBOX unread total for ambient presentation, plus Zerochi pending total/per-account pending counts for local transitions; contains no credentials or provider payloads.
- `PetPresentation`: mood, animation id, and selected copy. Copy remains outside engine logic.

## Ports

- `MailProvider`: identity, initial cursor, changes after cursor. It knows Gmail but not Zerochi.
- `SyncEngine`: serializes per-account sync, deduplicates `(accountId, messageId)`, commits messages and cursor atomically, categorizes recoverable/auth/history-expired errors.
- `AccountState` / `MailState`: normalized non-secret persistence and local pending transitions.
- `SecureStore`: refresh-token secrets keyed by stable local account UUID. The macOS implementation uses Keychain, provides set/get/delete, redacts errors, zeroizes temporary values, and never returns secrets across Tauri commands.
- `NotificationService`: displays already-decided notification content; never chooses mood.
- `ExternalNavigationService`: opens an account or exact message/thread without exposing browser account-position assumptions.
- `PetEngine`: pure snapshot/transition input to presentation output.

## React/Tauri boundary (planned commands)

`get_app_snapshot`, `add_account`, `remove_account`, `open_account`, `check_mail_now`, `open_message`, `get_preferences`, `update_preferences`. Events: `snapshot_changed`, `sync_status_changed`, `pet_event`. Commands return tagged, sanitized errors; logs exclude tokens, authorization codes, provider payloads, and message bodies. The approved normalized `From` and `Subject` metadata may enter only the native notification presentation described below; it never enters logs or a new React event/command result.

### `sync_status_changed` event

- Payload: `SyncStatusChanged { accountId, status, retryAfterSeconds? }`, matching `src/types/contracts.ts`. `accountId` is the stable local UUID already present in `MailAccount` and is the only approved correlation field.
- `status` is exactly `healthy`, `retrying`, or `action_required`. `retryAfterSeconds` is present only for `retrying`, is bounded by the Rust poll policy, and contains no provider data.
- Missing/locked/revoked credentials emit `action_required` only for the affected account. A recoverable network/provider failure emits `retrying`; the next successful committed poll emits `healthy` and clears the prior state for that account.
- The event must never contain email, display name, token material, provider response/error text, URL, cursor, message metadata, or adapter diagnostics. Receiving one account's event must not alter another account's status.

### `add_account` M4 contract

- Request: optional `{ provider }` with `"gmail"` (default when absent) or `"outlook"`; any other value fails with `config_invalid`. Outlook uses the Rust-only public `ZEROCHI_MICROSOFT_CLIENT_ID`, has no client secret, and returns the same result and error tags. OAuth configuration is Rust-only. Debug builds use process environment values first, then `dotenvy` to load both `ZEROCHI_GOOGLE_CLIENT_ID` and `ZEROCHI_GOOGLE_CLIENT_SECRET` from an ignored local `.env`. Release runtime ignores dotenv and receives both values at compile time through the protected wrapper; the wrapper uses a complete process/CI pair first or a complete ignored root `.env` pair for local packaging, never a mixed pair. React never supplies configuration, scopes, redirect URIs, client credentials, or token material.
- Success: `AddAccountResult { account: MailAccount }`, emitted only after the refresh token is stored through `SecureStore` and the non-secret account record is committed.
- Failure: `CommandError<AddAccountErrorTag> { tag, message, retryable, actionRequired }`. Messages are fixed and sanitized; no URL, email, provider body, environment value, callback data, code, verifier, state, token, account id, file path, header, or adapter error may cross the command boundary.
- Token-endpoint errors are classified only from an allowlisted provider `error` code. `invalid_client`, `unauthorized_client`, `deleted_client`, `invalid_scope`, `redirect_uri_mismatch`, `invalid_request`, and `unsupported_grant_type` map to `config_invalid`; `invalid_grant` maps to retryable `token_exchange_failed` so the user can start a fresh authorization. Provider descriptions, bodies, headers, and unknown fields are always discarded. A malformed successful response fails closed as `token_exchange_failed`.
- Debug builds may write one static allowlisted token-exchange diagnostic category to stderr for local acceptance, prefixed `zerochi.oauth.token_exchange`. The diagnostic is compiled out of release builds and must never interpolate provider text, status bodies, headers, client/account identity, URLs, codes, PKCE/state, or token material. Unknown provider errors collapse to a fixed `provider_error_other` category.
- For Google `invalid_request` only, a debug build may classify the discarded provider description through case-insensitive matching of fixed parameter names into static subcategories: missing `client_secret`, invalid `code_verifier`, invalid `redirect_uri`, invalid authorization `code`, or `invalid_request_other`. The original description and matched value are never emitted or retained; release remains a no-op.
- One add attempt may be active at a time in V1. A second request fails safely with `auth_in_progress`; it must not share or cancel the first attempt.
- User cancellation is idempotent and returns `cancelled` without persisting an account or secret.
- The allowed M4 tags are the `AddAccountErrorTag` union in `src/types/contracts.ts`. Adding or renaming a tag is a shared-contract change requiring Lead approval and a serialization test.

### Post-OAuth baseline and account hydration

- A successful `add_account` still means the refresh token and normalized account are durably committed. The returned `MailAccount` is sufficient for the current frontend session to upsert the account immediately; no secret or provider response crosses the boundary.
- After that durable commit, the command restores the main window, publishes the persisted snapshot immediately, and schedules a non-blocking first poll. The poll retrieves the refresh token through Keychain, establishes a baseline when the cursor is absent, creates no pending messages from historical mail, and then continues on the guarded scheduler.
- A baseline/network failure does not roll back valid OAuth consent or delete the committed account. The account remains visible with optional cursor/sync fields absent and is eligible for a guarded retry. This retry state is Rust-owned and sanitized.
- `get_app_snapshot` hydrates persisted normalized accounts on startup. Until that command is wired and consumed, account visibility after an application restart is not complete even if `accounts.json` is durable.
- React registers `snapshot_changed` before relying on hydration. A transient listener-registration failure triggers at most five cancelable retries with bounded exponential delays and a fresh `get_app_snapshot` read around successful registration. Live snapshot revisions prevent either read from overwriting a newer event; retries never create duplicate listeners and unmount cancels timers/late registrations. This is local Tauri lifecycle recovery, not frontend Gmail polling.
- Continuous reading requires all of: secure refresh-token retrieval, access-token refresh, one non-overlapping poll per active account, incremental history pagination, atomic message/cursor commit, and retry/backoff. An initial cursor alone must be reported as baseline, not as complete polling.
- Healthy accounts poll again 30 seconds after their prior poll completes. Due accounts run concurrently but remain individually guarded. Adding or removing an account wakes the central scheduler instead of spawning a competing per-account poll. Recoverable failures retain bounded per-account backoff up to 300 seconds.
- Gmail unread membership, newly normalized metadata, pending messages, and the History cursor commit atomically. If History/metadata processing fails, the prior unread set/messages/cursor remain authoritative and the last durable snapshot is projected before the sanitized sync status.

### OAuth completion lifecycle

- `add_account` restores the main popup best-effort after every terminal result, including success, cancellation, denial, timeout, configuration error, or storage failure. Native show/focus errors never replace the original command result.
- On success, `snapshot_changed` is emitted from durable local state before starting the immediate asynchronous poll. Therefore the connected account appears even if baseline or incremental Gmail access fails.
- `add_account` must not await Gmail baseline/history work after the secure token and normalized account commit. Polling owns baseline retry for accounts without a cursor and reports any later sync problem through `sync_status_changed`.

### M7 incremental mail state

- `accounts.json` schema v4 contains normalized `accounts`, Zerochi pending `messages`, and a Rust-internal bounded unread-message-id set per account in one document. The unread ids never serialize through commands/events. Older schemas migrate without guessing unread membership: active accounts require one baseline before incremental polling resumes, and migration never inflates pending or emits historical notifications.
- Persisted messages match `MailMessage`, contain metadata only, and are unique by `(accountId, id)`. Provider bodies, headers other than normalized From/Subject, access tokens, refresh tokens, and provider error payloads are forbidden.
- Incremental commit uses the expected previous cursor as a compare-and-swap guard. It deduplicates messages, recomputes pending from observed unopened messages, and advances cursor/time only when the whole state document is durable.
- Baseline, 404 recovery, and every successful incremental poll paginate `users.messages.list(labelIds=INBOX,q=is:unread)` as the authoritative bounded membership set. History remains the source of new-message candidates and the next cursor, but never guesses final label membership from unordered event arrays. The authoritative set, eligible new metadata, messages, and History cursor advance in one atomic CAS commit; failure to complete the list preserves the prior set/cursor/snapshot. Reading, re-unreading, archiving, moving to Spam/Trash, deleting, duplicates, and restart must converge to the same result as a fresh authoritative list.
- Only a newly added candidate present in the authoritative set is eligible for `users.messages.get(format=metadata)`, and its metadata response must still contain both `INBOX` and `UNREAD`. A message read or archived between list and metadata is removed before commit and produces no pending item or notification. The request names exactly `From`, `To`, and `Subject`; normalized `From`/`Subject` may enter the existing post-commit notification path, while `To`, provider payloads, body, snippet, parts, HTML/plain text, raw data, and attachments are discarded and never persisted.
- Poll authentication reads the refresh token only through a Rust-only zeroizing buffer and exchanges it for a memory-only access token using the same redacted Desktop client credential injected into the native build. It redacts missing/locked/provider failures. A successful one-shot poll is not continuous reading until a guarded scheduler invokes it for every active account and committed snapshots reach tray/UI consumers.
- `MailAccount.inboxUnreadCount` is the size of the locally persisted `INBOX + UNREAD` id set; no label-count endpoint is used. The sum across active accounts drives per-account/global numeric badges and the pet's ambient mood/face/copy. It does not change Zerochi `pendingCount` or local-open semantics.

### M9 native new-mail notification

- Eligibility is defined by persistence, not by Gmail unread totals or a before/after snapshot diff. A successful incremental compare-and-swap commit returns the exact messages it inserted after `(accountId,messageId)` deduplication; `PollOutcome` carries only those newly committed records to the Rust application coordinator. Baseline, expired-history recovery, startup hydration, unread-only changes, failed commits, and retries that insert nothing produce no notification.
- After publishing the same committed snapshot, the coordinator submits one best-effort native notification per newly committed message. A notification failure never rolls back the durable message/cursor commit and never causes that message to be replayed on the next poll. Repeated provider ids, overlapping polls, app restart, and snapshot rehydration must not duplicate delivery.
- `NotificationService` receives a Rust-internal bounded request derived only after that successful commit: stable opaque notification id, a process-local activation target containing stable local `accountId` plus bounded provider `messageId`, title = the persisted account email, subtitle = normalized message subject, body = normalized sender, and bundled custom sound `notification-chime`. Empty subject and sender use the fixed fallbacks `Sin asunto` and `Remitente desconocido`; subject and sender are truncated at a Unicode scalar boundary to at most 512 UTF-8 bytes before entering the native adapter. Only the opaque digest enters UserNotifications; provider ids, bodies/snippets, display name, provider payload/error text, token, authorization material, cursor, URL, and browser session position remain forbidden in the native notification response and logs. No new activation payload or target enters React.
- macOS maps those fields to native `title`, `subtitle`, and `body`, respectively. Native appearance controls exact font weight, but this yields the requested hierarchy: account first, subject second, sender last. This intentionally permits account email, subject, and sender to be visible in Notification Center and according to the user's macOS notification-preview settings; no additional mail content is retained for presentation.
- The supplied sound is a local application resource; it is not downloaded or read from mutable user state. It plays once when macOS accepts that notification for delivery. Permission denial, unsupported custom-sound behavior, and native adapter errors are sanitized and leave sync, pending, unread, and scheduling healthy.
- The native response returns only the validated opaque id. A bounded process-local map resolves it to `accountId + messageId`; duplicate ids never replace a target and synchronous delivery rejection removes it. Activation revalidates both account and message against the current durable snapshot, obtains the persisted `threadId` internally, requests one immediate guarded poll, and delegates to `ExternalNavigationService::open_message`. Missing, removed, mismatched, expired, or prior-process targets are silent no-ops. No new activation payload/event/DTO crosses to React; the existing normalized `AppSnapshot` remains unchanged. Email, provider id, thread id, URL, and activation target never enter native response metadata, logs, or errors.
- Exact navigation is best-effort because Gmail does not publish a stable Gmail Web message permalink. The native adapter attempts one strictly allowlisted HTTPS `mail.google.com` conversation deep link using the resolved identity and validated thread id; if native handoff rejects it, it attempts the existing account URL exactly once. A successful OS handoff does not prove which conversation Gmail rendered. Zerochi does not enumerate or control browser tabs, use Apple Events/Accessibility, or promise reuse of an existing Gmail tab.

### `open_account` M10 contract

- Request: `{ accountId }`, where `accountId` is the canonical stable local UUID already present in `MailAccount`. React sends only this identifier: it must not send email, browser index, URL, token, provider metadata, or a prebuilt navigation target. The command requests an immediate guarded poll for that account without awaiting Gmail, then performs the native handoff. Success returns unit after the native handoff is accepted; poll completion or failure never delays or replaces the navigation result.
- Rust validates the canonical UUID, reads the current persisted account record, and rejects a missing account before navigation. It resolves the account email internally and passes it only to `ExternalNavigationService`; the email never returns through a command/event and is never logged.
- `ExternalNavigationService` exclusively owns Gmail URL construction and native opening. For account navigation it selects the Google session through a percent-encoded `authuser` identity hint on an allowlisted HTTPS `mail.google.com` URL. Neither UI, commands, persistence, nor tests may encode or persist a positional `/u/N/` browser session index. The adapter must suppress child-process output and must not shell-interpolate the URL.
- Browser session state remains external: an already authenticated matching session opens that inbox; otherwise Google may ask the user to choose or authenticate an account. Zerochi never transfers OAuth access/refresh tokens to the browser and a successful handoff does not prove that Gmail ultimately displayed the requested account.
- Failure is `CommandError<OpenAccountErrorTag>` with only `account_not_found`, `navigation_failed`, or `internal`. Messages are fixed and sanitized; URL, email, account id, provider/browser output, filesystem paths, tokens, and adapter diagnostics must not cross the boundary or appear in logs. The poll request is best-effort and independent: a navigation failure may still leave that account eligible for immediate polling, while any later poll result follows the existing snapshot/status contracts.
- The existing TypeScript port remains `openAccount(accountId: AccountId): Promise<void>`. Exact message/thread navigation remains a separate `open_message` command and is not part of the account-row interaction.

### `check_mail_now` manual sync contract

- Request: no arguments. React must not enumerate accounts, send account ids/emails, or supply provider state. The command asks the central scheduler to make every currently active account immediately eligible, preserving the existing per-account non-overlap guard; repeated requests for an account already in flight coalesce into exactly one immediate trailing poll after that flight. Inactive or removed accounts are never made eligible or reinserted by a late completion.
- Success returns unit as soon as the scheduler accepts the request. It acknowledges `búsqueda iniciada`, not Gmail completion, new-mail discovery, or a refreshed unread value. Results continue exclusively through the existing durable commit, `snapshot_changed`, `sync_status_changed`, tray, and notification paths.
- Failure is `CommandError<CheckMailNowErrorTag>` with the sole tag `internal` and fixed sanitized copy. No account id/email, provider/browser response, token, cursor, message metadata, path, URL, or adapter diagnostic crosses the boundary or enters logs. Tauri's runtime `null` representation of Rust unit is normalized to `undefined` by the frontend adapter. The UI discards command-provided text, disables duplicate activation while the invoke is pending, bounds acknowledgement waiting to five seconds, keeps a fast successful pending indication visible for at least 800 ms, resets manual-sync feedback when leaving Settings, and uses only fixed local Spanish pending/success/failure copy. Real command failures and the five-second timeout are shown immediately rather than delayed for that presentation minimum.
- Forced checks do not bypass retry/auth policy, create overlapping polls, turn baseline/history recovery into new mail, duplicate notifications, or mutate Gmail. They only advance scheduler eligibility to now.

### `remove_account` M5 contract

- Request: `{ accountId }`, where `accountId` is the validated local UUID only. Success: `RemoveAccountResult { snapshot: AppSnapshot }` after local credential deletion and atomic removal of that account plus its messages. The command publishes the same committed snapshot to tray/UI.
- The implementation reads the refresh token only inside Rust, attempts bounded HTTPS revocation through Google's revoke endpoint, then deletes the Keychain item and normal state. Provider revocation is best-effort so an offline Google endpoint cannot trap local credentials; local Keychain deletion is mandatory before reporting success. Missing/already-invalid remote tokens are treated as revoked.
- Poll eligibility stops from committed account removal, and a racing poll may not recreate the account or its messages. Removing one account never changes another account's credentials, messages, cursor, pending, unread count, or sync status.
- Failures use only `account_not_found`, `secure_store_failed`, or `internal` with fixed sanitized messages. Refresh/access tokens, provider bodies, email, paths, and adapter errors never cross the command/event boundary.

### Native tray projection

- The macOS tray derives from normalized `accountCount`, global Zerochi `pendingTotal`, and the global Gmail unread total (still carried under the compatibility name `inboxUnreadTotal`); it never receives OAuth material, provider payloads, or frontend-only pet state.
- `accountCount == 0` is sleeping and renders `(-_-)` with no numeric counter. With accounts, the face/mood and numeric suffix follow the same summed Gmail unread count using the approved ranges `0`, `1–5`, `6–15`, `16–30`, `31–50`, and `51+`. Zero unread renders no number. This ambient projection never mutates Zerochi pending.
- Tray setup starts sleeping. The projection must be refreshed from persisted account state at startup, after `add_account`, and after every committed pending transition. A static startup title or an update only in the React session is incomplete.

### Native menu-bar popover

- The main window is initially hidden, non-resizable, transparent, and undecorated; macOS title-bar controls must not be visible. React must leave a transparent outer inset for the CSS shadow and top pointer rather than painting `:root`, `html`, or `body` opaque.
- A left-button press toggles the popup; release is ignored to avoid blur/release reopening. A visible popup closes on a repeated click in the same monitor; a click in another monitor transfers it under that clicked icon and focuses it. Hidden popups open under the clicked icon. macOS positioning uses a synchronous logical-point AppKit path based on the clicked tray window and target screen, avoiding the previous popup monitor's backing scale. Clamp to the current target screen's visible frame; a disconnected/missing screen must fail recoverably without blocking later clicks. Emit the unchanged `popover_anchor_changed { x }` after positioning; `x` is a bounded finite logical-pixel coordinate inside the window and contains no screen position, identity, or provider data. Delayed blur must recheck actual focus before hiding a newly transferred popup. Visibility/positioning/event failure is best-effort and must not replace an OAuth result.
- The bubble pointer is presentation-only and non-interactive. The home title remains accessible while visually hidden; Add account and Settings retain visible headings and all keyboard/focus semantics.
- Blur and close-request continue to hide rather than destroy the window. No Hand Mirror assets, camera visuals, or proprietary styling are copied; only the general anchored-popover pattern is reused.

## Invariants

Pending equals persisted messages with no `openedFromZerochiAt`, scoped to active observed messages—not Gmail unread. Opening is idempotent. The cursor advances only with successfully committed state. Account deletion removes normal state and invokes secret deletion as separate auditable work.

OAuth application configuration is supplied only through Rust-side build/runtime boundaries. No OAuth variable may use the `VITE_` prefix. Google credential JSON and `.env` files are never repository artifacts. An ignored local `.env` may contain the Desktop credential pair. Debug Rust parses it through `dotenvy` only when the process pair is absent. Production runtime never parses dotenv: `npm run tauri:release` resolves one complete pair from process/CI first or from the ignored root `.env` for local packaging, rejects partial/mixed sources, and passes the pair only into the protected native build. The Rust build script validates it and emits only a reversibly masked byte representation into generated native Rust. It must not use `env!`/`option_env!` for credential values because Cargo records those values in dep-info. The client credential may only enter a redacted, zeroizing Rust type and be sent to Google's token endpoint for authorization-code and refresh grants. It never crosses commands/events/logs. The wrapper enforces a fresh ephemeral Cargo target, scans textual artifacts for the raw value, and reports only the final bundle for upload; raw release builds fail closed and `target` is never cached/published wholesale. Refresh tokens persist only through `SecureStore`; access tokens and PKCE material remain memory-only.
